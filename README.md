# TAG

A smartphone-free connection between school, family and child. This repository contains the **one-school software pilot**: a parent PWA, school console, backend and virtual two-button TAG device.

Target deployment: `https://tag.trykobi.com`, on Andy’s VPS. Physical e-ink hardware is a later integration.

## Agreed behaviour

- Parents’ messages go straight through, including during school hours.
- `NOTICE`: a directive or inevitable event. The child can acknowledge with **GOT IT**; there is no pretend choice.
- `QUESTION`: a genuine choice. The child can answer **YES** or **NO**.
- Holding the left button for three seconds requests help. Both school staff and linked parents receive an in-app alert, with independent “seen” tracking. School staff resolve it after checking.
- No free-text child-originated messaging. One school, multiple families, multiple guardians per child, one active device per child.

## Included

- Staff and parent accounts, temporary password rotation, staff-managed family onboarding.
- Server-enforced guardian access checks; a paired device can only access its child’s messages and submit constrained responses/help requests.
- Expiring, one-use device pairing codes and device revocation.
- Durable message queue with queued, delivered, answered and expired states. Messages expire after 24 hours and are presented oldest first. Delivery is recorded after the device browser renders the message; it does not prove the child read it.
- Idempotent message submissions, immutable responses, deduplicated open help requests.
- Mobile layouts, installable web manifest, offline fallback. No API responses or child data are stored by the service worker.
- Hashed passwords and session/device tokens, HttpOnly cookies, origin and CSRF checks, rate limits and an audit log.
- PostgreSQL deployment using Docker Compose, Gunicorn and Caddy HTTPS. SQLite supports quick local development.

## Run locally

Python 3.12+:

```sh
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
python -m tag.manage init
python -m tag.manage demo
gunicorn --bind 127.0.0.1:8000 tag.app:app
```

The demo command requires an empty database and prints randomly generated passwords for `school@example.test` and `parent@example.test`. All demo people are fictional. Keep these passwords private. Open `http://localhost:8000` exactly; the default permitted origin is that address, not `127.0.0.1`.

For a blank pilot database instead of fictional demo accounts:

```sh
python -m tag.manage create-staff --email YOUR_EMAIL --name 'YOUR_NAME'
```

The initial password is requested privately at the terminal. Staff can then create parents and children under **People & devices**. Open `/device` in another browser window and enter a pairing code generated by staff.

## Verification

```sh
python -m unittest discover -s tests -v
node --check tag/static/app.js
```

Tests cover access isolation, origin/CSRF checks, account onboarding, pairing/revocation, expiry, valid response semantics, idempotency and alert recipients. Tests use a temporary SQLite database by default. For PostgreSQL, set `TEST_DATABASE_URL` to a **dedicated disposable test database**: tests delete its TAG rows before every test.

The browser smoke test starts its own disposable SQLite server on port 8765 and generates temporary credentials internally. Install the test dependencies with `npm ci` and `npx playwright install chromium`, then run `npm run test:browser`. It exercises desktop/mobile screens, pairing, notices, questions, long-press help and offline/reconnect behaviour. Screenshots are written to `/tmp/tag-school.png`, `/tmp/tag-parent-mobile.png` and `/tmp/tag-device.png` using fictional data only.

## Pilot boundaries

**Help alerts are in-app only.** The dashboards poll every five seconds while open, and browser background throttling can delay updates. There is no SMS, email, background web push, emergency-service call or guaranteed response time. The virtual device polls every three seconds while open. This build must not be relied upon as a safety-critical emergency system.

The parent PWA has a manifest and offline fallback, but intentionally does not queue offline messages or replies. A network failure is shown explicitly; it never claims successful delivery offline. Browser installation support varies.

Physical-device firmware/connectivity, attendance integration, school timetables, billing, multi-school tenancy and general chat are outside this pilot. Account recovery/disablement and staff creation use administrator commands. The data retention schedule must be agreed with the pilot school; no child records are silently purged. Before real-child use, arrange the school’s privacy/access review, backups and an operational plan for monitoring help requests.
